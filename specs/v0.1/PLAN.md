# PLAN — workbench-tauri v0.1

## 읽는 법과 이 순서에 걸린 규칙

**번호 표기.**
- `R-n`은 v0.1 `SPEC.md`의 요구 번호, `D-n`은 v0.1 `DECISIONS.md`의 결정 번호다.
- `03-tauri R-nn`은 03-tauri 출발 문서(D:\projects\docs\guides\zed-like-editor\03-tauri\README.md) 5절의 조사 항목이다.

**Phase 0(프로젝트 뼈대)을 둔다.** 작성자(wt-coder)가 제안했고 사용자가 골랐다(2026-11-01, SPEC 질문 Q8 A). 이유는 셋이다.
- 모든 PoC는 빌드·실행되는 Tauri 2 + Solid + Vite 프로젝트 위에서 한다. 그래서 그 준비를 PoC와 섞지 않고 따로 검증한다.
- D-10(CSP를 처음부터 켬)은 첫 빌드부터 걸려야 한다. 그러니 뼈대 단계의 완료 조건으로 둔다.
- workbench-gpui v0.1 PLAN도 같은 자리에 Phase 0을 두었다.

Phase 0은 03-tauri 7절에 없는 단계다.

**Phase 1(프레임워크·편집기 기반 PoC)을 7절 1단계보다 앞에 둔다.** 작성자가 제안했고 사용자가 골랐다(2026-11-01, SPEC 질문 Q9 A).
- 03-tauri 5.1은 P0 항목이 "하나라도 막히면 구조(프레임워크·편집기·구문 강조)를 다시 정한다"고 적었다.
- R-1(03-tauri R-01)이 실패하면 D-3이 React로 바뀐다(D-3). 그러면 그 위에 만든 타이틀 바·뼈대 UI를 다시 써야 한다. 그래서 프레임워크를 확인하는 PoC를 먼저 한다.
- R-2(03-tauri R-02)는 같은 CM6 PoC 위에서 이어서 한다.

**Phase 2·3은 03-tauri 7절 PoC 1·2단계를 그 순서대로 따른다.** v0.1 범위를 7절 PoC 1~2단계와 P0 항목으로 정한 것은 사용자 결정이다(2026-11-01, 질문 Q10 B).

**모든 Phase는 끝날 때 아래 순서를 밟는다.** 역할은 docs/HERDR-SETUP.md 4절을 따른다.

1. wt-reviewer(Codex)가 그 Phase의 `git diff`를 적대적으로 리뷰한다. 리뷰 항목에 Solid 반응성 함정(props 구조 분해 등)을 넣는다(D-3).
2. wt-checker가 그 Phase에 대응하는 R-n을 SPEC의 판정 방법대로 검증한다. 보고서는 `specs/v0.1/verify/`에 남긴다.
3. `PROGRESS.md`에 무엇을·결과·검증을 기록한다.
4. Phase 단위로 커밋한다(사용자가 골랐다, 2026-11-01, SPEC 질문 Q12 A).

**미해결 실패가 있으면 다음 Phase로 넘어가지 않는다.** 리뷰나 검증에서 해결하지 못한 실패가 남으면 다음 Phase를 시작하지 않는다. 그때는 작업을 멈추고 사용자에게 올린다(사용자가 골랐다, 2026-11-01, SPEC 질문 Q12 A).

**판정을 마친 것과 Phase를 마친 것은 다르다.** 대응하는 R-n을 모두 SPEC대로 판정하면 판정을 마친 것이다. Phase를 마치려면 대응 R-n마다 다음 둘 중 하나여야 한다. 마지막 Phase 3도 같다.
1. SPEC의 판정 방법대로 충족이다.
2. 사용자가 그 R-n을 이번 버전 범위에서 빼거나 다음 버전으로 넘기기로 정했다. 그 결정이 PROGRESS에 기록되어 있다.

다음 경우에는 Phase가 끝나지 않고 진행 중이다.
- 사용자에게 올리기만 하고 결정이 아직 없다.
- 사용자가 "해결 뒤 다시 판정"을 골랐다. 이때는 다시 판정해서 충족될 때까지 진행 중이다.

설계 결정이 바뀌면 DECISIONS에도 기록한다. 근거는 DOCUMENTS.md 7절 "요구를 만족시키는 Phase"와 위의 Q12 A 규칙(미해결 실패가 있으면 멈추고 사용자에게 올림)이다.

**"대기"는 미해결 실패가 아니다.** R-10의 Markdown·JSON 문법은 사용자가 Zed 앱에서 확장을 설치하기 전까지 판정을 대기한다(D-9, SPEC 질문 Q10 A). 대기인 채로도 Phase 3를 끝낼 수 있다. 설치된 뒤에 그 항목을 판정해 결과표와 PROGRESS를 갱신한다.

**작업을 끝낼 때마다 `PROGRESS.md`에 기록한다(루트 AGENTS.md 규칙).** 계획 밖 작업은 PROGRESS의 사용자 요청 작업으로 적는다.

## Phase 0 — 프로젝트 뼈대

**목적** — Tauri 2 + Solid + Vite + npm 프로젝트를 만들고, CSP를 켠 채로 빌드·실행되는 상태를 만든다. 03-tauri 7절에 없는 준비 단계다(사용자가 골랐다, 2026-11-01, SPEC 질문 Q8 A).

**대응** — 직접 대응하는 요구는 없다. D-3·D-4·D-10을 실행할 수 있게 하는 준비다. 관련: `D-3` · `D-4` · `D-10` · 03-tauri R-30 · 03-tauri R-31

**완료 조건**
- 레포 루트에 `package.json`과 `src-tauri/Cargo.toml`이 있다.
- 의존성에 `solid-js`와 Vite가 있고, `@tauri-apps/api`와 `tauri`의 마이너 버전이 같다(D-3, D-4, 03-tauri R-31).
- `package-lock.json`과 `Cargo.lock`이 저장소에 있다(D-4, 03-tauri R-31).
- Tauri 설정에 CSP가 켜져 있다(D-10).
- 빌드 준비물(Node, WebView2 런타임, MSVC, Rust)의 설치 여부와 버전이 PROGRESS에 기록되어 있다(03-tauri R-30).

- 위의 Phase 끝 순서(리뷰 → 검증 → PROGRESS → 커밋)를 마쳤다.
